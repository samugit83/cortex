**Working title:** *Cortex: Measurement-Gated Evolution and Pruning of Coding-Agent Skills*
(revisit after results; see [fallback framing](#7-risks-and-fallbacks))

**Argument (draft):** Coding agents are increasingly steered by hand-written
skills and rule files that nobody measures. Run-to-run noise is as large as the
effect of a single edit, so "try it and see" mistakes noise for improvement.
Cortex adds, removes and re-scopes skills only when a verifier-based,
statistically gated measurement supports it. We quantify agent noise, the error
rates of the acceptance gates against placebo controls, the held-out effect of
what each decision rule keeps, and the context that pruning saves.

### Research questions

| RQ | Question | Experiment |
|---|---|---|
| **RQ1** | How noisy is a coding agent's pass rate on the same task with the same harness? | POOL (base arm) |
| **RQ2** | How often do Cortex's gates keep a change that does nothing, or reject one that helps, compared with simpler rules at equal cost? | SIM + POOL |
| **RQ3** | Does what the gates keep improve performance on held-out tasks? | POOL + LOOP |
| **RQ4** | Can pruning and narrowing reduce always-on context without losing solve rate? | PRUNE |
| **RQ5** | What kind of skills survive measurement? | QUAL |
| **RQ6** | Can a calibrated judge predict, *before* a sweep is paid for, that a candidate will be rejected — where a free deterministic check cannot? | SCOPE (offline, no rollouts) |

### Primary endpoints (fixed before experiments, step 3.3)

1. **False-KEEP rate on placebo candidates**: Cortex gates vs the naive rule vs a textbook test (RQ2).
2. **Held-out pass-rate change** of the candidates each rule keeps (RQ3).

Everything else is secondary. Having two named primary endpoints protects the
paper from "we looked at 40 numbers and reported the best one".

**RQ6 is deliberately not a primary.** Cortex ships an optional judge in its
proposal layer, and it would be easy to over-claim for it. It is scored against
verdicts that already exist, it steers nothing that produces a primary number, and
its own validation (`jev/RESULTS.md`) may not exist when the paper is written. If
it is unvalidated, RQ6 reports the deterministic control only — which is still a
result, because that control demonstrably fails.

### Two paper sizes

| | Minimum publishable paper | Full paper |
|---|---|---|
| Contents | Design + SIM + noise study + pitfalls catalog + the boundary (§3.7) and SCOPE, both of which cost no rollouts | adds POOL gate reliability, held-out results, LOOP, PRUNE, QUAL |
| Rollouts | ~150 | ~1,300–1,700 |
| Judge | scored offline against existing verdicts (SCOPE); 0 rollouts either way | same |
| Story | "measuring agent-harness changes is harder than it looks, and here is a system that does it carefully" | the full measured-evolution story |

Plan for the full paper. The minimum paper is the fallback if the budget
shrinks or the held-out results are null, and it needs no extra work because
every part of it is also in the full paper.

## 3. Experimental design

### The core idea: measure a candidate pool once, evaluate every rule offline

Running a separate evolution loop for each baseline is expensive and weak: the
loops diverge after the first decision, and no candidate's *true* effect is ever
known. Instead:

1. Build a fixed **pool of candidate skills** per repo, including **controls with a
   known answer**.
2. Measure every candidate **once**, deeply: many runs on every task, train and
   held-out.
3. Apply each **decision rule** (Cortex gates at k=2/3, naive, textbook test,
   accept-all) **offline** by resampling runs from that data.

One dataset then answers RQ1, RQ2 and most of RQ3, every rule sees exactly the
same candidates, and adding a new rule later costs zero tokens.

### The experiments, in run order

| Name | What | Answers | Rollouts |
|---|---|---|---|
| **PILOT** | 1 repo, 4 tasks, base harness, k=10. Real cost per rollout, real noise, invalid rate. | budget, go/no-go | ~40 |
| **SIM** | Monte Carlo of every decision rule, including the two-stage screen → confirm, over pass rates, k ∈ {1,2,3,5,10}, #tasks ∈ {3,5,10,20}; later re-run with the pass-rate distribution measured in POOL. Ablation: drop each gate in turn. | RQ2 | 0 |
| **POOL** | Per repo: 10 tasks (6 train / 4 held-out). Base arm k=10 on all tasks. 6 candidates × k=5 on all tasks. | RQ1, RQ2, RQ3 | ~400 / repo |
| **LOOP** | 1 repo: 3–4 real `/evolve` cycles on train tasks, final harness vs base on held-out, k=10. Shows the whole system, proposal included, works end to end. | RQ3 | ~190 |
| **PRUNE** | 1 repo: an over-grown harness (~12 items) with planted controls; run `/prune`. | RQ4 | ~250 |
| **QUAL** | Code every candidate by category (procedure / domain knowledge / tooling / other) with a written codebook; second coder + Cohen's κ if possible. | RQ5 | 0 |
| **SCOPE** | Replay `cortex scope` over every candidate of every completed run and join the prediction with the recorded verdict and cost. Breadth is the control. `lab/bin/scope-replay`. | RQ6 | **0** |

### The candidate pool (per repo)

| Type | How many | Where it comes from | Why |
|---|---|---|---|
| Proposed | 3 | `/evolve`'s proposal step, run on harvested lessons | what Cortex would really test |
| Real-world | 1 | a skill from a public skill collection or community `CLAUDE.md` | "do popular skills help?", and avoids a straw-man baseline written by us |
| **Placebo** | 1 (2 if affordable) | plausible-looking but irrelevant advice of similar length | **true effect is zero by construction**: the only real ground truth for false KEEP |
| **Harmful** | 1 | advice that contradicts the project (e.g. skip running the tests) | known negative: checks that the regression gates catch it |

### PRUNE controls

Plant two kinds of items in the over-grown harness:
- **known-useless** (placebo) items: pruning should remove them;
- **one known-necessary** item: a project fact without which a specific task fails. Pruning must keep it.

This turns "pruning seemed to work" into a checkable claim.

### Statistics

- Tasks are the unit, not rollouts: bootstrap by resampling tasks (clustered), then runs within tasks.
- Robustness check: mixed-effects logistic regression `pass ~ arm + (1 | task)`.
- 95% CIs on every reported number; Holm correction across the primary endpoints.
- Held-out results are pooled across repos (4 held-out tasks per repo is too few on its own).
- The analysis plan is committed before POOL runs (step 3.3), and every deviation is listed in Appendix H.

| **Total, 2 repos** | **~1,280** | **~190M** |

Scale-down ladder, least damaging first:
1. Run everything on a cheaper model; repeat POOL on one repo with the stronger model.
2. 2 repos instead of 3.
3. 5 candidates instead of 6 (never drop the placebo or harmful control).
4. Candidate k from 5 to 4.
5. Drop LOOP (RQ3 then rests on POOL alone; say so in Limitations).

## 7. Risks and fallbacks

| # | Risk | Fallback |
|---|---|---|
| R1 | Held-out gains are null | Switch to the measurement-paper framing: noise, gate reliability against placebos, pitfalls, "unmeasured skills don't reliably help". A careful negative result is still publishable. |
| R2 | SIM shows a gate is badly calibrated | Fix it before the freeze (step 3.2) and report the redesign as a finding. |
| R3 | Too few harvested tasks | Lean on the public set; report the two sources separately. |
| R4 | Budget overrun | Scale-down ladder in §6; the minimum paper needs ~150 rollouts. |
| R5 | CLI or model changes mid-experiment | Pinned in step 2.1; `score.sh` already refuses a sweep that saw two CLI versions. |
| R6 | Public tasks are in the model's training data | Prefer post-cutoff or generated tasks; report public and harvested separately. |
| R7 | Placebo turns out to have a real effect | Report it: it shows how easily "irrelevant" text changes agent behaviour. Add a second placebo. |
| R8 | Prior work already does the core idea (G1) | Reposition on what is left: deletion/narrowing, placebo-controlled gate evaluation, pitfalls. |
| **R9** | **J0 never runs**, so the judge is unvalidated when the paper is written | RQ6 reports the deterministic control alone. "Glob breadth cannot separate a healthy item from a destructive one" is measured, needs no key, and stands on its own. Do **not** claim the judge works on the strength of the mechanism existing. |
| **R10** | **A reviewer reads "not an opinion, not an LLM judge" and then finds a judge in the repository** | §3.7 states the boundary before anyone has to go looking, and shows it is enforced by a test rather than by intent. The judge is off by default, absent from every primary, and scored in RQ6 rather than assumed. |
| **R11** | **The judge's model moves under a run** (`jev-latest` is an alias on a third party's server) | Any Jev-on run pins an exact version; `lab/bin/autopilot` refuses to start otherwise, and `roundcheck` emits a FINDING if two models answered in one round. Primaries are Jev-off, so they cannot be affected at all. |
