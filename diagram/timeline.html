why tasks live in the past

Today's skills, yesterday's problems

When you run /evolve (or /prune), it does not test your latest code. It rewinds to the exact moments things were broken and asks: can my skills solve these now? Here's why that's the only thing worth measuring.

The code travels back to each bug  ·  the skills stay fixed at today.

Your history, and the bugs you saved

Every time you fixed something, /harvest pinned a task to the commit just before the fix: the last moment the bug was alive.

What /evolve actually does

It carries today's skills backwards to each bug, and checks whether they can fix it.

Why not just test at HEAD?

Because you are not checking your code. You are checking whether Claude can solve problems.

✗ testing at HEAD

Everything's already fixed

At today's commit, every past bug is gone. Claude is handed a working repo and has nothing to do, so every task "passes" and you learn nothing about your skills.

Result: a perfect score that means nothing.

✓ rewinding to each bug

Real problems to solve

At each bug's own commit, the problem is live again, and every run proves it first: the task's check must fail before Claude starts, or the run is thrown out. Now the score is real: it shows whether your skills actually help Claude fix things it couldn't before.

Result: a score you can actually trust.

The optional judge: quick advice, never the verdict

Optionally, Cortex can ask a calibrated model (Jev) what to try. It never asks it what the result was, and the two live on very different time scales.

Cortex isn't asking "does my code work today?"
It's asking "do my skills help Claude solve real problems?"

So it re-opens old, already-solved problems as fresh challenges, each at the moment it was hard, and measures how today's skills cope.
