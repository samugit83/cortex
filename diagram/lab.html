Cortex · the lab

Does it actually work?

run D0 · the development run · one run, n = 1

Cortex claims it can learn your house rules from your corrections, and keep only the skills that measurably help. So we ran it for real — a working repository, real Claude sessions, ten rounds — and then gave it an exam it had never seen.

36%  →  76%

Tasks solved on held-out work — scenarios never shown to Cortex during learning — without the evolved skills, and with them. Three small files did that, at zero always-on context cost.

What these numbers are, and are not. This page reports D0, a single development run. Cortex itself was fixed 39 times while it ran, so the system under test moved; one run cannot separate “Cortex works” from “this run went well”; and the exam, though never shown to Cortex, was written by the same people who built the repository. The replicate runs, the control runs, the ablations and the gate calibration that answer those objections are specified in lab/BRIEF.md and have not been run yet.

D0 also predates the judge. Cortex has since gained an optional calibrated model in its proposal layer — which theme recurs, which tier fits, how much of the task suite a candidate is actually about. It is off by default, it took no part in anything on this page, and it is barred from the decision: cortex score, the six gates, check.sh and preflight contain no reference to it, and a test in Cortex's own suite asserts that. Every verdict below was reached exactly the way it would be reached today with the judge switched off.

1 the bench

A repository with rules a model cannot guess

To measure whether a skill helps, you need work where being right and being house-style are two different things — and a machine that can tell them apart.

shopkit — a small invoicing toolkit

70 unit tests, no dependencies, eight commits by two fictional teammates. Its house rules are written in CONTRIBUTING.md — a careful agent can find them — and enforced by make lint. Nothing in the repo ever reveals the answers.

The linter is the judge. Not a human, not Claude. Every number on this page comes from a script returning pass or fail, which is what makes them facts rather than opinions.

why family D exists

D is a trap for Cortex itself. There is no rule to learn, so the correct behaviour is to produce nothing. A system that invents skills to look busy would create one here. Across ten rounds, Cortex proposed zero candidates for D — and D scored 100% in both arms of the final exam.

2 a session

Everything starts with you correcting Claude

Not with a prompt, a config or a framework. Here is one real session from round 1, exactly as it happened.

  1. a teammate

    A failing test arrives

    QA commits a test: tax on a fractional rate like 8.25% comes out wrong. The bug is real — the old code throws away everything after the decimal point.

    shop/billing/tax.py the bug
    def tax_for(amount, rate):
    whole = int(rate.split(".")[0])   # 8.25 → 8
    return Money(amount.cents * whole // 100)
  2. you

    You ask Claude to fix it

    An ordinary request, in an ordinary chat. No mention of house rules — you would not think to mention them, and that is the point.

  3. Claude · Haiku 4.5

    It fixes the bug — and breaks the house style

    The arithmetic is now correct. Every test passes. And it is still wrong for this codebase, because money here is integer cents and Decimal is banned.

    the first attempt house rule broken
    + from decimal import Decimal
+ cents = int(Decimal(amount.cents) * Decimal(rate) / 100)
  4. CI

    The linter catches it

    make lint
    tests ........................ ok
lint: shop/billing/tax.py — Decimal is not allowed in billing/
CI is red
  5. you

    You correct it — this is the only teaching signal in the system

    your reply “The test passes now, but CI is still red: make lint rejects that arithmetic in shop/billing/. Use the helpers in rates.py.”

    Claude fixes it properly. Session over — the kind of exchange you have every day and forget by Friday.

    the corrected fix house style
    + from .rates import percent_of
+ return percent_of(amount, rate)
the raw material

Cortex never invents a rule. It only ever amplifies a correction you actually made. Of the 26 sessions in this lab, 17 contained one — and those 17 are the entire input to everything that follows.

3 /harvest · the task

Freeze that moment into something replayable

A session is a story, and you cannot measure a story. /harvest turns it into a task: a checkpoint you can drop any agent back into, forever.

.evolve/tasks/01/  — the real one, from the session above
task.yaml
base_sha: 2b5173a — the commit before Claude touched anything. Rewind here and the bug is alive again.
prompt.txt
What you asked, word for word. Replayed identically every time, so runs are comparable.
check.sh
The judge: the new test + the whole suite (no regressions) + make lint (the house rule). Returns pass or fail, nothing else.
fix.patch
The reference fix — proof the task is solvable at all.
notes.md
What went wrong, and which skills cover that area.
the detail that makes it work

check.sh runs both the tests and the linter. A check that ran only the tests would have passed the Decimal version too — and would be blind to the exact thing we are trying to teach. The correction is what turns a test into a house-rule test.

Ten rounds produced 27 tasks and 17 lessons. Now there is a ruler.↓
4 /evolve · the candidate

Write one skill aimed at what keeps recurring

Cortex reads the lessons, finds something that happened more than once, and writes a proposal. It is staged, not installed — nothing is live yet.

Two billing corrections → one rule

Round 1 produced two lessons about the same thing: money arithmetic in shop/billing/. Cortex wrote a rule scoped to exactly those files — its name, its wording and its scope all chosen by the model, unattended.

candidate · .claude/rules/use-billing-helpers.md
---
name: use-billing-helpers
paths: ["shop/billing/**"]
---
Never use float, round() or Decimal in shop/billing/.
Scale money only with the helpers in billing/rates.py.
staged, not live

This file sits in a holding area. Nothing has been proved yet, and Cortex is not allowed to install it on the strength of it sounding reasonable — which, notably, it does.

5 the measurement

The same jobs, twice: with it and without it

This is the heart of Cortex, and it is the oldest idea in science — a controlled comparison, where exactly one thing differs between the two worlds.

First, what a rollout is

One rollout = one complete headless Claude session, alone in a throwaway clone of the repository, rewound to a task's broken commit, handed that task's prompt, with no human present. When it stops, check.sh scores it 1 or 0. Then the clone is deleted.

Your working copy is never touched. This lab ran 1,230 of them.

Why every task is run three times

Claude is not deterministic: the same prompt can pass once and fail the next time. So each task is run k times per arm and the score is an average — 0, 0.33, 0.67 or 1.0. One run proves nothing; three runs tell you whether an effect is real or a coin flip.

1 · the screen
a cheap first filter
~12 rollouts~$1~1 min
  • only the tasks that are currently failing
  • k = 2
  • may say “worth confirming” or “dead”
  • may never approve anything
→
2 · the confirm
the verdict that counts
138 rollouts~$9.50~10 min
  • every task in the suite, not just the broken ones
  • k = 3
  • this is where damage elsewhere shows up
  • says KEEP or KILL
why two stages

A screen only looks at broken tasks, so it cannot see what a skill breaks — which is why it is allowed to kill but never to approve. It is also optimistic: in round 3 the screen measured a gain of 1.5 and the confirm measured 0.67. The screen throws away losers for a dollar; the confirm decides.

6 the gates

Five questions. One “no” and it is buried.

The confirm produces numbers; the gates turn numbers into a verdict. Every gate below actually fired in this lab — the red box names the candidate it killed.

1
Did it help at all?
At least one task has to get better. “It feels cleaner” is not a result.
enforce-shop-clock
gain 0 — helped nothing
2
Did any single task get much worse?
A drop bigger than the tolerance kills it, even if the average improved.
changelog-rule-v2

3
Did it break work it has nothing to do with?
The protected set: everything that already passed must keep passing. This is the gate that does the real work.
clock-in-billing
broke 10 unrelated tasks
4
Is the gain bigger than noise?
A win of one lucky run is not a win. The net has to clear a floor.
the floor: net ≥ 2 runs
5
Did the model even use it?
A candidate that sat in context and was never opened cannot have caused the difference — so the difference was noise.
changelog-updates
in context 10× · used 0×
and a sixth answer

Sometimes the right verdict is neither: RERUN — “the measurement itself was broken, decide nothing.” It fires when, for instance, no target task could possibly have passed. It is the safety valve that stops a tooling failure from being recorded as “this idea is bad”.

7 two twins

The best argument for measuring anything

These two files came out of the same lab, for the same house rule, with the same name and the same scope. One is dead. One is live today. Read them and try to tell which is which.

✗ buried.evolve/graveyard/
---
name: check-changelog-on-shop-edits
description: When editing shop code,
  verify CHANGELOG.md is updated for
  user-visible changes
paths: ["shop/**"]
---

When you modify files in the shop
directory, verify that the change is
user-visible. If it introduces a new
feature or a user-facing change:

1. Check whether CHANGELOG.md has been
   updated under [Unreleased]
2. If not, add a brief entry
3. Put it in the same commit
In context in 6 of 6 rollouts. Chosen by the model 0 times.
✓ live.claude/skills/
---
name: check-changelog-on-shop-edits
description: Before finishing changes
  to shop/ code, verify CHANGELOG.md
  was updated
paths: ["shop/**"]
---

1. After modifying shop/ code, check if
   CHANGELOG.md needs an entry.
2. If you added a user-visible feature or
   fix, ensure CHANGELOG.md has an
   [Unreleased] entry describing it.
3. If [Unreleased] is missing, add it at
   the top of the file.
4. Do not skip it for refactoring users
   would notice.
Same scope, same instructions. Worth +67 points on its family.

Same name. Same paths. Near-identical bodies. The only meaningful difference is the highlighted line — the description, the one part the model reads before deciding whether to open the file at all.

“When editing shop code…” describes a condition.
“Before finishing changes…” describes a moment.

A condition is something the model can always argue it is not currently in. A moment is something it notices arriving. That is the entire difference between a dead skill and a live one — and no amount of reading either file would have told you. Six rollouts and a counter did.

why the dead one is kept

The graveyard is not a bin of old drafts. Nothing in it loads, and it costs nothing. It exists so that: the same experiment is never run twice; a retry must take a new name, keeping the record unambiguous; a sweep can refuse to re-test a buried idea unmeasured; and after a model upgrade you can ask the question again — with the old score to compare against.

10 the finding

Getting into the room beats being well written

Every rollout records what was available to the model and what it actually used. Across 123 rollouts of the exam, that gap turned out to be the whole story.

ItemIn contextActually used
use-billing-helpersrule5252 / 52
complete-exporter-setupgated skill2720 / 27
check-changelog-on-shop-editsgated skill1237 / 123

A rule does not have to be noticed — when the agent opens a matching file it is simply there, and it worked every single time. A skill has to be chosen, and it gets chosen when its description names the task at hand (“when implementing a new exporter”: 20 of 27) and ignored when it names a side duty (“verify the CHANGELOG was updated”: 7 of 123, and 0 of 10 as an always-on skill).

the uncomfortable part

The changelog skill was opened 7 times in 123 rollouts and still moved its family by 67 points. Its description alone, sitting in context, appears to be doing the work its body was written to do. Nobody designed that. The measurement found it anyway — which is rather the point of measuring.

11 honesty

What this proves, and what it does not

✓ What the lab shows

  • On unseen work, the evolved harness raised the solve rate from 36% to 76%.
  • It added nothing to the family that needed nothing, and broke nothing there.
  • It refused seven of its own ten ideas, including the highest-scoring one.
  • Tier beats wording: rules fire every time, skills only when their description names the job.
  • The whole loop cost $155 and ran unattended.

△ What it does not show

  • One model, one repository, one experimenter. Every number is conditional on all three.
  • Nine scenarios per family is a small exam. The confidence intervals are wide; the +44 is the weakest.
  • The house rules here are machine-checkable. Rules that need judgement were never tested.
  • The sessions were driven by a script that plays a user faithfully but never gets confused.
  • Family E ended with nothing. A user with that problem would finish ten rounds empty-handed.
  • n = 1. One run, on a Cortex that was fixed 39 times while it ran. Replicates, controls and ablations are specified but unrun.
The most expensive thing on this page is family E. Four attempts at one house rule — read the time through shop.clock — cost 694 rollouts and $77.70 and landed nothing. Each was killed for the same reason: it helped its own family and broke something else, because a rule scoped to shop/** is injected into every task in that tree, including the great majority that have nothing to do with time.

That failure is visible before a sweep is paid for, and it is what cortex scope was built to report. The obvious free version does not work: over these ten candidates, what a glob reaches overlaps between the items that were kept (19%, 50%, 96%) and the items that were buried for breaking things (12%, 12%, 46%, 58%, 96%). What separates them is the share of injections that are actually about the candidate — and that is the one quantity here that needs a model. Whether a model can compute it is an open question, scored against this run's own verdicts by lab/bin/scope-replay, and it is not answered yet.
